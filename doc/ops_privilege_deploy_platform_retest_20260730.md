# Ops-Privilege 部署平台复测报告（2026-07-30）

## 测试目标

模拟真实用户在服务器上运行 `ops-privilege` 模式，输入“帮忙部署平台”，确认高权限计划并观察是否能够完成 Klonet 平台启动。

连接方式：`ssh -b 10.47.123.69 -p 1012 lzl@192.168.1.33`
项目目录：`/home/lzl/klonet_agent`
Conda 环境：`klonet_agent`

## 主要结论

当前版本相比上一版有明显进步：

1. CLI/控制命令可以正确处理 UTF-8 BOM，不再把 `confirm-priv` 当作普通自然语言请求。
2. `manage_process` 可以接受 `SIGTERM/SIGKILL` 等 POSIX 信号写法，不再因为 `SIGTERM` 与 `TERM` 格式不一致被拒绝。
3. 同用户进程终止不再错误使用 `sudo kill`，避免非交互环境下卡在 sudo 密码。
4. `port_owner` 证据现在能输出同一监听端口的全部 PID、tree root PID、PGID、SID、cwd、cmd，对 gunicorn 多 worker 结构更可靠。
5. 恢复链路新增了确定性端口冲突修复计划：当 `start_platform_screens` 因端口占用失败，且只读证据证明端口被旧 Klonet 实例占用时，可以生成 `manage_process(scope=process_group)` + 重新启动平台的修复计划。
6. 修复了 step 级确认状态机问题：计划级确认后，step 会被正确置为 `awaiting_confirmation`，`confirm-priv-step` 不再被错误拒绝。

但平台启动仍未完整完成。当前真实环境中旧 test 实例具有更复杂的残留/自恢复行为：终止旧 master 进程组后，端口 45551 又被新的 gunicorn master PID 占用，同时 5005 仍有 web_terminal 残留进程。继续盲目 kill 可能扩大影响，因此本轮停止在诊断阶段。

## 已修改代码

- `app/cli.py`：新增 `clean_user_input`，清理 BOM/零宽字符。
- `ops/privileged/supervisor.py`：控制命令路由前统一规范化用户输入。
- `ops/privileged/planner_schema.py`：新增进程信号规范化与终止信号集合。
- `ops/privileged/planner.py`：复用信号规范化生成 `manage_process` 后置检查。
- `ops/privileged/action_runner.py`：支持信号别名、同用户直接 kill、可选 `scope=process_group`。
- `tools/environment.py`：`port_owner` 输出全部监听 PID、tree root、PGID、SID。
- `ops/privileged/workflow.py`：修复 step 确认状态，新增端口冲突确定性恢复计划生成器。
- `ops/privileged/checkers.py`：`process_pid_absent` 对 signal 后 zombie 状态不再误判为普通运行进程。
- `ops/actions.py`：更新 `manage_process` 能力描述。

## 剩余问题

1. 首轮部署计划仍不会在执行前主动处理端口占用，端口冲突主要依赖失败后的恢复链路。
2. 确定性恢复目前只处理 `start_platform_screens` 失败，不处理 `manage_process` 自身失败后重新从当前端口状态规划。
3. 旧 test 实例可能由 daemon 化 gunicorn 或外部脚本重新拉起，需要进一步识别再拉起来源，而不能只 kill 当前 PID/PGID。
4. `start_platform_screens` 的文案曾出现“不会修改服务器环境”的描述，但实际会创建 screen 和启动服务，应修正文案/风险描述。
5. 当前环境中已有多个历史测试残留进程，继续执行清理前应明确哪些属于可删除的旧实例，避免误停用户仍在使用的服务。

## 建议下一步

1. 增加 `stop_klonet_runtime_instance` 专用注册动作：输入 `cwd/project_root/ports`，内部一次性定位并终止同 cwd 下 master、worker、web_terminal、相关 PGID，并验证目标端口释放。
2. 在 `start_platform_screens` 前置阶段输出结构化端口 owner 证据，或在 planner 初始上下文中包含运行端口占用情况。
3. 增加旧实例自恢复来源 probe：检查 gunicorn pidfile、screen、crontab、systemd user service、supervisor、nohup 日志等。
4. 为 `confirm-priv` -> `confirm-priv-step` 状态流补专门 workflow 单测，避免状态机回归。

## 当前状态

本轮测试没有完成 Klonet 平台最终启动。Agent 质量较上一版明显提升，但在复杂旧实例残留场景下仍未达到“完整自动部署平台”的验收标准。当前阻塞点不再是中文输入或基础控制命令，而是旧 Klonet runtime 清理能力建模不足。
