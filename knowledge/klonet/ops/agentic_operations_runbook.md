# Klonet Agentic 运维 Runbook

本文只提供经验与检查思路，不定义必须执行的工作流。Planner 必须结合用户目标、
当前知识检索结果和服务器事实自主决定路线；任何条目都可以被跳过、重排或替换，
但必须说明依据并给出可观察的成功标准。

## 通用原则

- 先区分源码包目录、平台运行目录与部署实例目录，不能仅凭目录名猜测。
- 缺少事实时先做注册的只读探测，不能用写操作“试试看”。
- 已完成步骤及其环境改动是后续规划的事实，重规划不能假定它们未发生。
- 启动、停止、配置、升级和回退都要检查真实状态，不把退出码等同于业务成功。
- 共享服务、端口、进程、Screen、Nginx 路由和 Git 状态可能互相影响，应按证据
  决定是否联合检查。

## 常见任务的经验

部署或启动平台时，通常需要确认项目布局、运行目录、入口文件、Python 环境、
共享服务和端口，再准备运行文件、启动组件并检查进程、Screen、端口或健康接口。
Klonet 的源码包可能位于 `vemu_uestc/`，而入口文件位于其 `mains/` 下并需要准备到
同级平台运行目录；必须以当前源码与环境事实为准，不能把这一经验写死成固定步骤。

停止或重启时，应先识别明确实例和组件，记录当前进程与监听状态，再执行最小范围
的停止或重启，并确认旧进程消失、新进程及其工作目录和端口符合预期。

配置 Nginx 时，应确认实际配置目录、站点启用方式、目标上游和端口。配置变更后先
做语法检查，再决定是否重载，并从路由响应或监听状态验证结果。

安装或修复基础环境时，应先盘点操作系统、磁盘、Python、Docker、虚拟化能力和
已有服务。软件包、安装脚本、容器及服务变更分别验证，不假定整套安装脚本适用于
当前主机。

源码获取、升级或回退时，应确认仓库、分支、工作区改动、目标修订和运行实例。
更新代码不等于部署完成；是否需要准备运行文件、迁移配置或重启由当前差异决定。

共享服务故障时，应联合检查配置中的主机与端口、宿主机监听、Docker 映射、服务
状态和日志。Redis、MySQL、RabbitMQ 等名称相同并不代表是同一实例。

## 失败后的经验

步骤失败后，停止尚未执行的变更，把实际执行绑定、退出结果、检查结果、已发生的
环境改动、已完成与剩余步骤组成 Failure Packet。Verifier 可追加安全的只读证据并
给出反思；同一个 Planner 根据这些事实重新规划。新路线必须与失败路线有实质差异，
否则等待用户决定，不能无限重复。

一次性 Shell 只用于注册 Action 无法覆盖的单个语义步骤。脚本必须固定内容、工作
目录、执行用户、环境、超时、哈希和到期时间，经解析器安全检查后逐步展示给用户
确认；脚本只能执行一次，环境指纹变化或内容变化时必须失效。
