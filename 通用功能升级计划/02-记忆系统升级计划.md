# Klonet Agent 记忆系统升级计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use `subagent-driven-development` (recommended) or `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**目标：** 将 Klonet Agent 从 Markdown 全量注入与整篇覆盖，升级为以 PostgreSQL + pgvector 为唯一权威存储、可版本化、可检索、可审计、按需注入的记忆系统。

**架构：** 原始对话和工具事件继续作为证据源；独立写入管线从事件中提取记忆候选，经作用域、隐私、去重、冲突和时态校验后，以事务写入 PostgreSQL。读取侧使用结构化过滤、全文检索、向量检索和可选 rerank 生成小型 `MemoryPack`，再交给 `ContextCompiler` 注入本轮上下文。

**技术栈：** Python 3.8+、PostgreSQL、pgvector、SQLAlchemy/Alembic 或等价迁移工具、现有 embedding/rerank 客户端、pytest。

### 1.2 为什么先关闭这些问题

记忆召回最终仍要通过 `ContextCompiler` 进入模型。如果硬预算、checkpoint 覆盖范围和恢复路径不可靠，数据库检索得再准，也可能被重复历史挤掉或导致每轮重复压缩。因此推荐顺序是：

```text
关闭上下文 P0 遗留
→ 建立数据库记忆写入
→ 建立数据库记忆召回
→ 将 MemoryPack 接入 ContextCompiler
→ 联合评估上下文与记忆
```

## 2. 本计划范围

本文覆盖“当前任务状态”之前的记忆能力：

1. 情景记忆；
2. 长期语义记忆；
3. 用户画像；
4. 记忆写入与更新；
5. 冲突、版本和过期；
6. 记忆召回；
7. 按需注入。

本文不重新设计当前任务 checkpoint。`TaskCheckpoint` 属于上下文恢复状态；数据库记忆属于跨回合、跨 session 的可复用信息。两者必须分开：

| 类型 | 回答的问题 | 生命周期 | 是否每轮注入 |
| --- | --- | --- | --- |
| TaskCheckpoint | 当前任务做到哪一步、下一步是什么 | 当前任务 | 是，保持很小 |
| 情景记忆 | 过去某次具体任务发生了什么 | 跨 session | 否，按需检索 |
| 语义记忆 | 当前仍有效的项目事实是什么 | 跨任务 | 否，按需检索 |
| 用户画像 | 用户有哪些稳定偏好 | 跨项目或按项目 | 否，只注入相关偏好 |

## 3. 当前实现基线

当前记忆主要由 `memory/store.py` 管理：

```text
history.jsonl          原始会话历史
YYYY-MM-DD.md          当天情景记忆
MEMORY.md              项目长期记忆
memory/users/{user_id}/USER.md  用户画像
memory/shared/ops/*.md  共享 Ops 历史记录
```

当前行为：

- `append_episode` 向当天 Markdown 追加自然语言块；
- `write_memory` 整篇覆盖 `MEMORY.md`；
- `write_user` 整篇覆盖 `USER.md`；
- 完整 `MEMORY.md` 和 `USER.md` 每轮进入 system prompt；
- 普通 Mentor/Coding 情景记忆没有与知识库等价的混合检索；
- 共享 Ops 记忆只有轻量关键词搜索；
- 记忆是否写入、如何融合主要由主模型临场决定。

现有设计值得保留的部分：

- 已有 `user_id/project_id` 作用域；
- 已区分个人、项目和共享 Ops 数据；
- 运行态证据高于历史记忆的规则已经明确；
- 原始历史和 trace 可以作为记忆来源；
- 已有 BM25、embedding、RRF 和 rerank 基础设施；
- 已有敏感信息不得进入记忆的安全合同。

## 4. 目标架构

```text
对话/工具/项目日志事件
          │
          ▼
 MemoryCandidateExtractor
          │ 结构化候选
          ▼
 MemoryWritePolicy
  ├─ 作用域校验
  ├─ 敏感信息过滤
  ├─ 稳定性/重要性判断
  └─ 来源完整性校验
          │
          ▼
 MemoryConsolidator
  ├─ 查找相似现有记忆
  ├─ ADD / UPDATE / SUPERSEDE / NOOP / REJECT
  ├─ 冲突与时态处理
  └─ PostgreSQL 事务写入
          │
          ├────────► embedding outbox ─► pgvector
          ▼
 PostgreSQL：唯一权威记忆存储

当前用户输入
     │
     ▼
 MemoryRetriever
  ├─ user/project/mode/time 过滤
  ├─ PostgreSQL 全文检索
  ├─ pgvector 语义检索
  ├─ RRF/规则融合
  └─ 可选 rerank
     │
     ▼
 MemoryPackBuilder
     │ 有界、带来源、去冲突
     ▼
 ContextCompiler
```

核心原则：

1. PostgreSQL 是记忆事实的唯一权威存储。
2. Markdown 只用于一次性迁移、人工导出和灾难恢复，不参与运行时决策。
3. 主模型不能直接执行任意数据库写入。
4. 每条记忆必须有作用域、类型、来源、版本和有效期。
5. 旧事实不直接覆盖删除，而是失效或被新版本替代。
6. 召回先做权限和有效性过滤，再做相关性排序。
7. 向量相似只表示“相关”，不表示“真实”或“当前有效”。
8. 记忆是历史线索；涉及服务器当前状态时仍必须重新调用工具确认。
9. Memory Pack 有独立 token 预算，不允许完整数据库内容常驻 prompt。

## 5. 数据库设计

### 5.1 为什么选择 PostgreSQL + pgvector

PostgreSQL 负责：

- 事务和并发；
- 用户、项目和模式作用域；
- 版本、失效和来源关系；
- JSONB 扩展字段；
- 全文检索；
- 行级权限和备份。

pgvector 负责：

- 记忆内容 embedding；
- cosine/L2 等相似度检索；
- exact search 或 HNSW/IVFFlat 近似索引；
- 与 PostgreSQL 过滤条件组合；
- 和全文检索组成 hybrid search。

官方 pgvector 文档明确支持向量相似搜索、条件过滤、HNSW/IVFFlat、全文混合检索和多租户分区策略：<https://github.com/pgvector/pgvector>

### 5.2 核心表

#### `memory_records`

代表一条逻辑记忆的当前身份，不直接保存可变正文：

```text
id                  UUID primary key
user_id             text not null
project_id          text nullable
scope               user | project | shared_ops
memory_type         episode | fact | preference
subject_key         规范化主题键
status              active | superseded | expired | deleted
active_version_id   UUID
importance          real
confidence          real
created_at          timestamptz
updated_at          timestamptz
```

#### `memory_versions`

保存不可变版本：

```text
id                  UUID primary key
memory_id           UUID foreign key
version             integer
content             text
summary             text
metadata            jsonb
embedding           vector(n) nullable
embedding_model     text nullable
embedding_version   text nullable
content_hash        text
observed_at         timestamptz
valid_from          timestamptz
valid_to            timestamptz nullable
created_at          timestamptz
```

有效时间属于版本而非逻辑记录。这样同一逻辑记忆的不同历史版本可以分别回答“当时有效的事实是什么”。`memory_records.active_version_id` 只指向当前版本。

#### `memory_sources`

将记忆结论关联回原始证据：

```text
memory_version_id   UUID
source_type         history_event | tool_result | journal | user_statement
source_id           text
source_excerpt      text
observed_at         timestamptz
```

`source_excerpt` 必须经过脱敏并限制长度，原始完整证据仍保存在原事件系统中。

#### `memory_relations`

首版只保存必要关系，不上图数据库：

```text
from_memory_id      UUID
relation_type       supersedes | supports | contradicts | related_to
to_memory_id        UUID
confidence          real
created_at          timestamptz
```

#### `memory_write_candidates`

保存待处理候选及决策结果，方便审计：

```text
id                  UUID
source_event_range  jsonb
candidate_payload   jsonb
decision            add | update | supersede | noop | reject
decision_reason     text
processed_at        timestamptz
```

#### `memory_embedding_outbox`

保证正文事务提交与 embedding 异步生成解耦：

```text
memory_version_id   UUID
status              pending | processing | completed | failed
attempt_count       integer
last_error          text
next_attempt_at     timestamptz
```

### 5.3 作用域和数据库安全

所有查询必须先绑定 `user_id`，项目记忆还必须绑定 `project_id`。应用层过滤之外，生产部署应启用 PostgreSQL Row-Level Security，避免遗漏过滤条件导致跨用户读取。PostgreSQL 官方文档说明，启用 RLS 后，普通访问必须满足对应 policy：<https://www.postgresql.org/docs/current/ddl-rowsecurity.html>

生产连接使用无 `BYPASSRLS` 权限的应用角色。每个事务开始后用 `SET LOCAL` 写入当前 `user_id/project_id`，事务结束自动清除，禁止把租户变量留在连接池会话中。`shared_ops` 只允许 Ops 服务角色读取；迁移/备份管理员使用独立角色和独立连接池，不与在线请求共用。

数据库不得存储：

- 密码、API Key、cookie、Authorization；
- 私钥或 `.env` 正文；
- 未脱敏工具输出；
- 未经授权的其他用户信息；
- 模型隐藏推理内容。

## 6. 逐项优化设计

### 6.1 情景记忆：从日期 Markdown 升级为原子 Episode

#### 优化什么

当前某一天的多个任务追加到同一个 `YYYY-MM-DD.md`，检索粒度是整份文件或关键词片段。升级后，每次有复用价值的具体经历形成一条原子 `episode`：

```text
发生了什么
为什么发生
采取了什么行动
结果是什么
哪些证据支持结果
有哪些失败尝试
后续什么时候可能有用
```

#### 原理

情景记忆的价值在于复用“某个具体经历”，而不是复述某天的全部聊天。原子化后可以独立检索、评分、过期、关联来源，也可以只召回真正相关的事件。

Mem0 将长期对话记忆设计为动态抽取、整合和召回显著信息，而非持续携带完整会话；A-MEM 则将记忆组织成带属性和链接的原子 note。参考：

- <https://arxiv.org/abs/2504.19413>
- <https://arxiv.org/abs/2502.12110>

#### 好处

- 检索粒度更准确；
- 不同任务不会因同一天记录在一起而互相污染；
- 能记录失败方法，减少重复踩坑；
- 能按项目、时间、问题类型和结果过滤；
- 能回溯到原始对话或工具证据。

### 6.2 长期语义记忆：从整篇 MEMORY.md 升级为版本化事实

#### 优化什么

把项目不变量、架构事实和稳定结论保存为独立 `fact`，不再让模型整篇覆盖 `MEMORY.md`。

示例：

```text
subject_key: project.python_version
content: 当前项目运行时要求 Python 3.8
scope: project
confidence: 0.95
valid_from: 2026-07-01
source: config.py/tool evidence
```

#### 原理

长期语义记忆是从具体经历中提炼出的、当前仍有效的事实。每条事实拥有稳定身份和不可变版本，事实发生变化时创建新版本或 supersede 旧事实，而不是重写整篇文档。

2026 年记忆综述将 Agent 记忆概括为 write—manage—read 循环，并指出写入过滤、矛盾处理、遗忘和隐私治理是生产系统的关键问题：<https://arxiv.org/abs/2603.07670>

#### 好处

- 不会因为模型漏抄而丢失其他长期事实；
- 可精确定位哪条事实发生了变化；
- 支持来源、置信度和有效期；
- 可以只召回与当前问题相关的事实；
- 支持回滚和审计。

### 6.3 用户画像：从整篇 USER.md 升级为有作用域的稳定偏好

#### 优化什么

用户画像不再是一份长期累积文本，而是多个独立 `preference`：

```text
编码风格偏好
回答详细程度
常用开发环境
工具选择偏好
项目特定约束
```

每条偏好必须区分：

- 全局稳定偏好；
- 仅某个项目有效的偏好；
- 一次任务中的临时要求。

临时要求只进入 TaskCheckpoint 或当前 turn，不写成用户长期画像。

#### 原理

偏好只有在用户明确表达、重复表现或确认后才应持久化。把临时命令误写为稳定画像，会让后续任务持续受到错误约束。因此写入策略需要稳定性阈值和作用域判断。

#### 好处

- 避免把一次性要求永久化；
- 不同项目可以拥有不同偏好；
- 用户可以查看和删除单条画像；
- 修改某条偏好不会覆盖其他画像；
- 每轮只注入当前任务需要的偏好。

### 6.4 记忆写入：从主模型直接写文件升级为候选—决策管线

#### 优化什么

取消主模型直接执行 `write_memory`、`write_user` 的权威能力。模型只能提出结构化候选，最终写入由受控管线决定：

```text
事件范围
→ 提取候选
→ 敏感信息过滤
→ 判断是否值得长期保存
→ 检索相似现有记忆
→ ADD / UPDATE / SUPERSEDE / NOOP / REJECT
→ 数据库事务
→ embedding outbox
```

建议写入动作：

- `ADD`：新增独立事实或经历；
- `UPDATE`：同一逻辑记忆产生新版本；
- `SUPERSEDE`：新事实明确取代旧事实；
- `NOOP`：已有等价记忆；
- `REJECT`：临时、敏感、缺少来源或不可信。

#### 原理

让主模型自由决定“写什么、怎么覆盖”把数据完整性交给概率模型。更稳妥的方式是让模型只负责语义候选，Python 和数据库负责权限、唯一性、版本和事务。

Mem0 的生产型路线强调从对话中提取并整合显著信息；AgeMem 则进一步把 store、retrieve、update、summarize、discard 作为明确记忆动作。参考：

- <https://arxiv.org/abs/2504.19413>
- <https://arxiv.org/abs/2601.01885>

#### 好处

- 写入过程可审计；
- 能统一去重和冲突处理；
- 模型失败不会直接破坏正式记忆；
- embedding 失败不影响正文事务；
- 可以统计候选接受率和误写率。

### 6.5 冲突、版本与过期：从“模型自行融合”升级为时态事实

#### 优化什么

每条事实区分：

- `observed_at`：什么时候获得证据；
- `valid_from/valid_to`：事实在现实中何时有效；
- `created_at`：数据库何时记录；
- `status`：active/superseded/expired/deleted。

例如项目从 Python 3.8 迁移到 3.11：

```text
旧事实 valid_to = 迁移时间，status = superseded
新事实 valid_from = 迁移时间，status = active
新事实 --supersedes--> 旧事实
```

默认查询分成两种模式：

- `current`：只返回当前时刻 active 且有效的版本；普通问答默认使用；
- `as_of(timestamp)`：返回指定时间有效的历史版本；仅在用户询问历史状态或审计时使用。

冲突处理按记忆类型执行：

1. 项目/运行态事实：当前工具证据高于历史记忆；
2. 用户偏好：用户本轮明确修正高于旧画像，工具证据不得替用户决定主观偏好；
3. 情景记忆：保留各自事件，不因结果不同而互相覆盖；
4. 同类型、同来源中更晚且已验证的事实优先；
5. 无法判定时两者均保留为 `contradicts`，召回时明确提示不确定；
6. 模型不得静默合并互斥事实。

#### 原理

现实事实会变化，旧记忆并不总是“错误”，可能只是已经过期。版本和有效期比覆盖删除更能表达变化，也能避免旧向量继续被当成当前事实召回。

A-MEM提出 memory evolution，让新记忆触发旧记忆属性和连接的更新；本项目采用更保守、可审计的版本关系，而不是让模型静默改写旧正文：<https://arxiv.org/abs/2502.12110>

#### 好处

- 新旧事实不会同时作为有效结论注入；
- 可以回答“以前是什么、现在是什么”；
- 误更新可以回滚；
- 冲突不会被模型悄悄掩盖；
- 时间问题和迁移问题的回答更准确。

### 6.6 记忆召回：从完整注入或简单关键词升级为混合检索

#### 优化什么

为普通 Mentor/Coding/允许使用记忆的 Ops 流程建立统一 `MemoryRetriever`：

```text
第一步：硬过滤
user_id / project_id / scope / query_mode / status / valid time / sensitivity

第二步：多路召回
PostgreSQL 全文检索
+ pgvector 向量相似度
+ subject_key/实体精确匹配
+ 最近相关 episode

第三步：融合
RRF 或可解释加权

第四步：可选 rerank

第五步：去冲突和 token 裁剪
```

建议召回得分考虑：

```text
semantic relevance
+ lexical relevance
+ scope match
+ recency
+ importance
+ confidence
- expired/conflict penalty
```

#### 原理

向量检索擅长语义近似，但对版本号、路径、端口、API 名等精确词可能不稳定；全文和精确检索擅长字面命中。混合检索可以覆盖两类问题，再通过 RRF/rerank 统一排序。

pgvector 官方建议与 PostgreSQL 全文检索组合，并可使用 RRF 或 cross-encoder 融合结果：<https://github.com/pgvector/pgvector#hybrid-search>

中文全文检索不能直接依赖 PostgreSQL 默认英文词典。首版复用项目现有 `jieba` 分词，将规范化 token 写入 `lexical_text`，用 `simple` configuration 建立 `tsvector`；技术标识符、路径和版本号额外进入精确匹配字段。

#### 好处

- 记忆不再全部常驻上下文；
- 同时兼顾自然语言问题和技术精确词；
- 先过滤作用域，降低跨用户和跨项目泄漏；
- 可以复用项目已有 embedding、RRF 和 rerank 经验；
- 召回路径和分数可以 trace。

### 6.7 按需注入：从完整 Markdown 升级为有界 MemoryPack

#### 优化什么

`MEMORY.md` 和 `USER.md` 不再完整进入每轮 system prompt。`MemoryPackBuilder` 根据当前问题生成固定预算的小包：

```text
相关用户偏好：最多 2 条
相关项目事实：最多 4 条
相似历史经历：最多 3 条
冲突或过期提示：按需
```

每条内容包含：

```text
memory_id
类型和作用域
简短内容
有效时间/置信度
来源引用
```

Memory Pack 作为独立 `evidence_messages` 区进入 `ContextCompiler`，不能伪装成 system policy。条数是候选上限，token 上限是最终硬约束；二者冲突时以 token 上限为准，并整条淘汰最低分记忆，禁止截断单条结构。

#### 原理

检索到的记忆只是与当前任务相关的历史信息，不应拥有系统规则的优先级。按需选择并设置独立 token 预算，可以减少注意力干扰和每轮重复成本。

Mem0 的论文报告其记忆方案相对 full-context 显著减少 token 和延迟，但这是论文实验结果，本项目必须通过自己的 Klonet eval 验证：<https://arxiv.org/abs/2504.19413>

#### 好处

- 降低每轮 token 消耗；
- 避免无关长期事实干扰当前推理；
- Memory Pack 可被 ContextCompiler 独立裁剪；
- 来源明确，模型能区分历史线索和当前证据；
- prompt cache 不再被不断增长的整篇 Markdown 破坏。

## 7. 写入和读取接口

建议建立数据库无关的领域接口，但正式运行只提供 PostgreSQL 实现；单元测试使用 in-memory fake，不维护 SQLite 正式后端。

| Repository 方法 | 职责 |
| --- | --- |
| `add_candidate(candidate) -> str` | 保存待审计的写入候选 |
| `add_record(command) -> MemoryRecord` | 创建新的逻辑记忆 |
| `add_version(command) -> MemoryVersion` | 为已有记忆创建不可变新版本 |
| `supersede(old_id, new_id) -> None` | 在同一事务中建立替代关系并失效旧事实 |
| `search(query) -> list[MemoryHit]` | 执行已绑定作用域的混合检索 |
| `get_active(memory_id) -> MemoryRecord | None` | 读取当前有效版本 |
| `mark_expired(memory_id, valid_to) -> None` | 将记忆标记为过期而不删除历史版本 |

组件边界：

```text
memory/domain.py          纯领域模型，不依赖数据库驱动
memory/repository.py      Protocol 与查询/命令对象
memory/postgres.py        PostgreSQL 实现
memory/write_pipeline.py  候选提取和 consolidation
memory/retriever.py       混合召回
memory/pack.py            有界注入包
memory/migration.py       Markdown 一次性迁移
```

### 7.1 写入决策的确定性边界

- `subject_key`：由 `memory_type + scope + 规范化实体 + 属性名` 组成，例如 `fact:project:demo:python_version`；episode 使用事件 UUID，不按主题覆盖。
- `importance`：只表示未来复用价值，不表示事实正确性；由枚举规则映射为数值。
- `confidence`：来自来源等级；用户明确陈述、工具验证、模型推断分别使用不同上限。
- `verified`：必须存在用户明确陈述或成功工具证据；仅 assistant 自述不能标为已验证。
- `UPDATE`：同一事实含义未变，只补充描述、来源或置信度。
- `SUPERSEDE`：同一 subject 的有效值发生变化，旧版本结束有效期。
- `NOOP`：内容 hash 等价，或新来源不能增加信息/置信度。
- `REJECT`：候选敏感、临时、无作用域、无来源或不具复用价值；拒绝只记录在 candidate 表，不创建正式 record。

### 7.2 写入触发点

正常触发点是“一个用户回合及其工具循环成功持久化之后”。先提交原始事件，再异步提交候选提取任务；候选失败不影响用户回答。session 结束和 checkpoint 只负责扫描尚未处理的事件区间，不能重复处理已有 source range。显式用户要求“记住/忘记”走同一 policy，但提高候选优先级，不绕过敏感信息和作用域校验。

### 7.3 embedding 模型与维度

第一版数据库只允许一个 active embedding profile（模型、版本、维度）。`memory_embeddings` 独立于正文版本，以 `(memory_version_id, embedding_profile_id)` 唯一。更换维度时创建新 profile、新索引并后台重嵌入；新旧 profile 可并存，但一次查询只使用一个 profile。完成覆盖率和召回评估后再切换 active profile，不原地改变已有 vector 维度。

## 8. Markdown 迁移策略

迁移来源：

- `memory/sessions/*/*/MEMORY.md` → `fact`；
- `memory/users/*/USER.md` → `preference`；
- `memory/sessions/*/*/YYYY-MM-DD.md` → `episode`；
- `memory/shared/ops/*.md` → `shared_ops episode/fact`。

迁移要求：

1. 先只读扫描并生成报告；
2. 每个源文件计算 hash；
3. 解析结果进入 `memory_write_candidates`；
4. 候选经同一去重、冲突和敏感过滤管线；
5. 导入使用唯一键保证幂等；
6. 导入后对比源记录数、接受数、拒绝数和原因；
7. 迁移期间采用明确状态机，不允许双权威：`legacy`（Markdown 权威）→ `shadow`（数据库影子写入、回答仍读 Markdown）→ `compare`（双读对比、仍以 Markdown 回答）→ `cutover`（PostgreSQL 唯一权威）；
8. cutover 回滚只能回到最近数据库导出的只读快照，不恢复双写；
9. 不自动删除旧文件。

3. **`attach_sources`：UPDATE 有两种落地形态**。§7.1 的 UPDATE 含"只补充来源"，
   而版本表上有 `(memory_id, content_hash)` 唯一约束，"同一段正文一个记忆里只存一份"。
   所以内容等价时挂来源（`attach_sources`）、内容变了才追加版本（`add_version`），
   `apply_plan` 按内容哈希自动分派。
4. **`replace_active` 是 SUPERSEDE 的唯一正确落地方式**。§6.5 的迁移例子要求新旧
   记忆同 `subject_key`，而部分唯一索引 `uq_memory_records_active_subject` 不允许
   同时存在两条 active——"先 add_record 再 supersede"走不通。必须在同一事务里
   「旧记录转 superseded → 封旧版本有效期 → 插新记录 → 建关系」。
5. **`add_version` 会给上一版封口**（`valid_to = GREATEST(new_valid_from, old_valid_from+1µs)`）。
   §6.5 没写这条，但不封口的话 `as_of` 查询会对同一 subject 返回两条"当时有效"的记录。
   同时修了 `search` 的 as_of 视图：它原先带着 `r.active_version_id = v.id`，
   导致时态查询永远只能返回当前版本（等于没实现）。
6. **`mark_expired` 收紧为只对 active 记忆生效**。阶段 1 的实现无条件更新"当前版本"的
   `valid_to`，对一条已被替代的记忆调用它会把一个已封存版本的时间窗再改一次
   （记录状态因 `status='active'` 条件不变），是一次静默的历史篡改。
7. **状态机把 superseded/expired/deleted 定为终态**。§6.5 只列了四种状态、没写迁移规则。
   终态不可复活，同一 subject 再次成立时创建**新的**逻辑记录——这同时保证 `valid_to`
   只被写一次。

## 11. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 模型误写长期事实 | 候选与正式写入分离；来源、置信度和稳定性门控 |
| 向量相似被误认为事实正确 | 向量只参与召回；有效性由状态、时间和来源决定 |
| 新旧事实冲突 | version、valid time、supersedes/contradicts；不能静默覆盖 |
| 跨用户数据泄漏 | Repository 强制作用域 + PostgreSQL RLS + 隔离测试 |
| embedding 服务失败 | outbox 重试；正文先提交；全文检索降级 |
| HNSW 过滤后召回不足 | 首版 exact search；实测后启用 iterative scan/分区/partial index |
| 数据库不可用拖垮聊天 | 明确超时；非必要记忆召回可降级为空包；不得伪造记忆结果 |
| Markdown 迁移重复或丢失 | 源 hash、幂等键、预览、事务和迁移核对报告 |
| 删除权难以落实 | 逻辑删除、物理清理任务、embedding 同步删除和审计记录 |
| 记忆无限增长 | 类型化保留策略、过期、归档和定期质量审计 |

## 12. 暂不采用的设计

### 不直接接入 Mem0 服务

采用其抽取、整合、召回思想，但不把权威数据交给外部框架。原因是项目已经有明确的用户/项目隔离、Ops 证据等级、RAG 和审计合同，需要本地可控的数据模型。

### 不在第一版使用图数据库

`memory_relations` 足够表达 supersedes、supports、contradicts 和 related_to。只有当多跳关系查询在 eval 中证明有收益，才考虑将关系派生同步到图数据库。

### 不立即启用 HNSW

记忆规模较小时 PostgreSQL exact vector search 更简单且召回完整。HNSW 是性能优化，不是功能前提；多租户过滤下还需关注过滤后候选不足。应先测量，再建索引。

### 不维护 SQLite 正式后端

正式系统只维护 PostgreSQL 语义。单元测试使用 fake repository，集成测试使用临时 PostgreSQL。避免两套 SQL、全文检索和向量实现长期漂移。

## 14. 决策摘要

本次升级不是把 Markdown 内容原样搬进数据库，而是改变记忆生命周期：

```text
旧：主模型决定写记忆
    → 整篇覆盖 Markdown
    → 每轮完整注入
    → 冲突靠模型自行理解

新：事件产生结构化候选
    → policy 过滤与 consolidation
    → PostgreSQL 事务保存原子版本
    → pgvector + 全文混合检索
    → 生成有界 MemoryPack
    → 作为历史证据进入 ContextCompiler
```

PostgreSQL + pgvector 的角色不是单纯“向量数据库”，而是同时承担记忆的结构化事实、版本、时态、来源、权限、全文与语义检索。这样既能获得向量召回能力，又不会牺牲关系数据库对正确性和审计的保障。
