# Klonet Agent 开发与架构收敛规范

本文档是 Klonet Agent 的开发约束入口，适用于人工开发者和 Coding Agent。
目标不是记录某次故障的修法，而是保证后续修改持续减少概念、收敛调用链，并且能够被测试证明。

## 1. 权威性与适用范围

发生冲突时，按以下顺序判断：

1. 当前代码中的结构化合同、安全策略和自动化测试；
2. 本文档；
3. 最新版架构设计文档；
4. README、知识库和运维手册；
5. 带日期的历史设计稿、迁移说明和旧实现备注。

历史设计稿只解释演进背景，不能据此恢复已经删除的兼容路径。发现本文档与当前代码不一致时，必须先确认这是实现回退还是规范过期，再在同一变更中修正其中一方，禁止长期双轨。

## 2. 总原则：架构收敛优先

每次修改都应使系统概念更少、职责更清楚、调用链更统一。禁止为了尽快覆盖一个话术、目录、端口、组件或报错而增加旁路。

具体要求：

- 优先修正或统一已有抽象，不立即新增 Planner、Replanner、Verifier、Coordinator、状态机、Decision 类型或并行工作流。
- 同一种架构概念只能有一个权威实现。数据可以有不同生命周期，但不能有多个模块同时决定同一件事。
- 规则应表达系统不变量，例如“等待人工选择时禁止进入语义路由”，而不是“输入 `1` 时执行某函数”。
- Prompt 可以帮助模型提出候选语义，不能代替状态、权限、Schema、注册表、审批和验收约束。
- 修复完成后删除被替代的分支、类、字段、兼容入口和测试夹具，不以“暂时保留”为由维持双轨。
- 新增代码量应与删除、合并或显著简化的旧路径相匹配。只有真正新增的独立能力可以例外。

### 2.1 新增模块的准入条件

新增模块前必须同时证明：

1. 现有模块在语义上不应承担该职责；
2. 扩展现有模块会违反单一职责，或造成比新边界更严重的耦合；
3. 新模块会替代或删除至少一条旧路径，而不是与旧路径长期并存。

无法证明时禁止新增。若任务明确要求先征得用户同意，则在创建文件前停止并提交证据。

## 3. 修改前必须完成的分析

开始编辑代码前，完整阅读受影响调用链，而不是只看报错行。至少回答：

- 当前行为由哪些入口、状态存储、领域模块和输出模块负责；
- Planner、Binder、Executor、Checker、Verifier、Coordinator 和状态模型各自承担什么职责；
- 根因属于实现错误、职责缺失，还是抽象边界错误；
- 哪些旧职责、分支或数据结构会被删除或合并；
- 修改后的唯一调用链是什么；
- 为什么不需要新增并行模块。

推荐在动手前提交以下短模板：

```text
根因所在的抽象层：
应修改的现有模块：
准备删除或合并的重复职责：
为什么不新增模块：
修改后的唯一调用链：
需要维持的系统不变量：
```

不得用“先加特判让它工作，再研究架构”跳过这一步。

## 4. 当前唯一工作流及职责

Ops-Privilege 的权威调用链是：

```text
精确控制命令 / 持久化待决状态门
  → Intent Classifier 提出语义候选
  → Coordinator 用真实状态核对并选择现有工作流
  → Discovery 收集只读证据
  → Evidence Synthesis 组织证据
  → Planner ↔ Discovery 形成语义计划
  → Binder 绑定受控实施能力
  → 精确计划审批
  → Executor 单次执行
  → Checker 收集后置条件
  → Verifier 判断目标级结果
  → Response 整理终态答案
```

失败后只能在同一主循环中局部 Replan，或形成 `FailureRecord` 进入人工决策；不得另起一套失败工作流。

| 概念 | 唯一职责 | 禁止承担的职责 |
| --- | --- | --- |
| Intent Classifier | 根据当前输入和受控上下文提出意图、目标关系和范围候选 | 凭关键词决定真实计划状态、批准执行或覆盖持久化目标 |
| Coordinator | 组合阶段、核对候选路由与持久化现实、维护唯一调用链 | 自行生成事实、计划或最终只读结论 |
| Operational Context | 保存可恢复的当前目标、意图、证据和活动计划引用 | 把历史 assistant 文本升级为事实或计划 |
| RuntimeInventory | 按 `project_root` 统一实例身份、角色、端口和运行态关系 | 用平台名、目录片段或枚举关键词猜测实例身份 |
| Discovery | 通过 Probe Registry 执行只读补证 | 规划变更、执行 Action、拼 Shell、决定目标完成 |
| Evidence Synthesis | 只基于已有证据形成声明、缺口和因果链 | 调工具、创造事实、决定是否执行 |
| Planner | 描述语义变更、依赖、影响和成功标准 | 选择 Action、写命令、批准或执行计划 |
| Binder | 把已冻结语义步骤映射为注册 Action 或正式 `ShellArtifact` | 修改用户目标、用实现便利性重写语义计划 |
| Executor | 按已审批的冻结绑定执行一次并记录证据 | 规划、自动重试未知执行、宣布目标完成 |
| Checker | 验证单个后置条件或步骤事实 | 代替 Verifier 判断整个用户目标 |
| Verifier | 产生唯一的目标级 `GoalOutcome` | 修改环境、补写计划、用回答措辞掩盖失败 |
| Response | 将已确认事实和结果整理成用户可读答案 | 补证、执行建议命令、重新打开工作流或改变结果 |

### 4.1 完成状态的命名边界

`GoalOutcome.status == "achieved"` 是唯一的“用户目标已完成”判据。其他状态只在各自层级有效：

- `ChangePlan.status == "completed"`：计划执行生命周期结束；
- Checker 的 `passed`：某条验收标准通过；
- Planner 的 `ready`：候选计划信息足够进入下一阶段。

这些词不得互相推导。步骤通过不代表目标完成，计划执行结束也不代表目标已达到。跨层转换必须由 Verifier 基于目标和证据完成。

分层实施计划中的组件效果同样只有一套完成判据：原子 Action 成功只证明动作已执行，
组件必须同时通过该语义步骤声明的健康、端口、进程或 Screen 验收后，才能进入可跨
Replan 继承的 `completed` ledger。若外层语义验收失败，所属组件原子节点必须回到
`paused`；恢复旧计划时也按同一规则对账。禁止外层失败、内层仍作为已完成效果被过滤。

## 5. 路由、上下文与停滞状态

### 5.1 分类器只是候选，不是状态权威

自然语言分类不可避免会出错，因此分类结果必须接受持久化状态核对：

- “状态”“运行”“计划”等关键词不得直接决定路由；必须理解动作、对象、否定、纠正和对上一目标的关系。
- 用户说“不是重启”“不要继续旧计划”时，否定约束必须进入目标模型，旧目标不得因关键词再次出现而复活。
- “继续”“重试”“刚刚到哪了”等省略表达应从 `OperationalContext`、PlanStore 和 FailureRecord 恢复真实目标；不能从 assistant 自己的历史承诺恢复虚构状态。
- 一个计划是否存在、是否可确认、是否已被替代，只能查询 PlanStore，不能由 LLM 猜测。
- 分类器提出了现实中不存在的 Plan 路由时，Coordinator 应拒绝该候选或恢复持久化目标，不得编造计划。

### 5.2 待人工决策是状态门，不是关键词特判

最新未处理的 `FailureRecord` 是停滞状态的唯一权威。进入该状态后：

- 只接受记录中实际存在的选项序号、完整标签、显式 `option_id`、详情命令和取消命令；
- 选项数量来自持久化数据，不硬编码为 `1/2/3`；
- 其他自然语言不得落回 LLM 分类器，也不得启动新目标；
- 选中后立即持久化 `selected_option_id`。`continue_current_goal` 和 `cancel`
  立即完成该次人工转移；`provide_direction` 只表示进入“等待边界输入”，
  在 `user_direction` 持久化前 FailureRecord 仍是活动状态；
- 等待边界时，下一条语义输入必须写回该 FailureRecord 并携带原目标、
  失败缺口和已尝试路径返回原 Plan/Replan 循环，不得重新进入普通意图分类；
- 恢复动作回到原 Plan/Replan 主循环，不创建旁路执行路径。

如果产品以后允许用户在停滞时开启新目标，应增加一个明确的“放弃当前失败并开始新目标”状态迁移，而不是让任意文本穿透状态门。

### 5.3 精确审批

计划审批必须绑定 Plan ID、完整可执行内容的哈希和当前状态。裸文本“确认”“同意”既不能修改计划，也不能批准旧哈希。计划修订必须废弃旧可执行版本，重新规划、绑定并产生新的 ID 或哈希；对话中的草案不属于可执行计划。

## 6. 证据与运行时事实

- 当前运行态工具结果高于历史对话、共享记忆、RAG 和静态文档。
- assistant 历史只用于理解对话，不是已验证事实库。
- RAG 提供领域知识和排查方向，不得宣称某台服务器当前正在运行什么。
- 每项确定性声明必须能追溯到 `EvidenceRecord` 或明确的持久化状态。
- Discovery 优先调用已注册的只读 Probe；未注册的长尾只读检查允许由 LLM
  提出单条命令候选，但必须经过确定性只读策略校验、拆成固定 argv，并通过
  `ValidatedReadonlyCommandRunner` 执行。命令候选不能绕过领域 Probe 已定义的
  证据语义，也不能包含 shell 运算符或产生环境修改。
- `ProbeRequest` 必须尽量表达 `required_facts` 和运行态 `freshness`，而不只给出
  Probe 名。`required_facts` 是证据合同，不是 Shell 兜底触发器。首次注册
  Probe 产出可用证据后必须先返回 Planner/Verifier；只有它们看过该证据后
  仍以结构化合同提出同一未满足事实，或注册能力不存在/执行不可用时，
  Discovery 才评估补充只读命令。Planner、Binder 和 Verifier 的补证都必须经过
  同一个 Discovery 边界。
- 重复 Probe 由稳定 cache key 去重。达到预算前也要检测“没有新证据”的循环，不能靠提高轮数掩盖不收敛。
- 诊断必须给出可验证的因果链；“缺少证据”应对应具体目标判据，而不是看到任意 uncertainty 就拒绝完成。
- `RuntimeInventory` 是实例关系的权威模型。平台名、进程、screen、端口、cwd、配置和项目目录必须通过真实关系归属于同一个 `project_root`。
- `running_platforms` 已提供精确 `project_root`、受管角色、端口、运行身份和组件启动合同时，Planner 必须直接消费 `RuntimeInventory`，不得把字段措辞差异当作事实缺失并重复请求同一 Probe。
- 工具失败表示 `unchecked` 或证据不可得，不能解释为对象不存在。

## 7. 规划、绑定与执行边界

### 7.1 Planner

Planner 只描述“要改变什么、为什么、依赖什么、预期影响和如何证明成功”。它不能看到或输出具体 Action 名、Shell 命令和审批决定。需要更多事实时返回结构化 ProbeRequest，并由 Discovery 执行。

计划必须满足：

- 每个步骤有明确的 expected changes 和 postconditions；
- 依赖关系可验证且无循环；
- 资源引用来自运行时证据，不凭历史路径或常见端口补全；
- 语义不自相矛盾，例如“重启角色”和“保留健康角色不重启”不能同时存在；
- 同一运行时不变量只能有一个语义编译入口。例如“重启后由 Screen 管理”和“把现有角色收编为 Screen 管理”都要求以 Screen 所属进程替换当前运行时，必须进入同一个组件生命周期计划；不得因用户没有使用“重启”这个字面词而退化到另一套自由规划路径；
- 用户要求使用 Screen 时，验收必须证明 Screen 会话及其进程归属，而不只证明端口监听。

### 7.2 Binder 与注册 Action

Binder 独占实施能力选择。注册 Action 优先，参数合同必须完整、可冻结、可审计。出现以下情况时必须回到补证或 Replan，不能改走等价旁路：

- Action 参数缺失或不合法；
- 权限/helper 合同不匹配；
- 前置条件不满足；
- 执行失败或 Checker 未通过；
- 现有 Action 的语义其实覆盖目标，只是当前调用不方便。

高频、稳定、可复用的能力应收敛成参数有界的 Action。不得为单个目录、端口、组件名或话术复制一个近似 Action。

注册 Action 的语义、必需参数和结构性验收条件由 Action 合同唯一负责。LLM 可以补全
候选参数或提出额外的目标级观察，但不得用一组非空候选 Checker 覆盖注册合同。例如
`prepare_project_files` 的入口文件集合必须从 `REQUIRED_ENTRY_FILES` 生成；不得根据
通用 Web 框架经验追加 `manage.py` 等 Klonet 合同之外的文件。参数最终冻结后，程序
必须重新生成依赖这些参数的权威前置/后置条件，再交给 Verifier 执行。
当注册 Action 的核心参数可由冻结资源确定性编译时，必须先运行资源编译器，再让 LLM
补充无法推导的长尾参数；不得要求 LLM 先判断已冻结参数“能否绑定”。多实例资源必须
按 semantic-step consumer 隔离，禁止从步骤话术中的数字猜端口，或把 `master_pid`、
`worker_pid`、端口和根目录跨实例组合。

### 7.3 LLM 自主 Shell 兜底的唯一边界

项目允许 LLM 为未注册的长尾能力自主生成 Shell 兜底，但“自主生成”不等于
“绕过合同直接执行”。只读和变更分别进入现有的两个权威边界：

- 只读请求：LLM 可以提出一个确定性只读命令；系统校验风险并用 `shlex`
  解析为 argv，随后由 Executor 使用 `shell=False` 执行。它不能使用管道、重定向、
  命令替换或其他 shell 求值，也不能取代已经定义了目标语义的领域 Probe。
- 变更请求：Binder 先评估注册 Action；没有 Action 覆盖语义目标时，必须继续让
  LLM 评估一次性 `ShellArtifact`，不能仅以“没有注册 Action”为由提前阻塞。
  Artifact 通过完整合同、安全校验和人工确认后由 Executor 执行。

因此，禁止的是未进入上述边界的“隐式 Shell”，不是禁止 LLM 自主设计兜底实现。

严禁以下实现：

```python
# 错误：绑定失败后拼字符串执行
command = f"cd {cwd} && {program} {args}"
subprocess.run(command, shell=True)
```

也不得在合同之外把若干命令用 `&&`、管道、命令替换、嵌套 shell 或临时脚本
拼成未建模的执行路径。注册 Action 只是实现选择之一；如果它在语义上不覆盖目标，
应正常转入 `ShellArtifact`。如果已经选定的 Action 只是参数不合法、权限失败、执行
失败或验收失败，则应先把真实失败交回补证/Replan，不能偷偷拼一条 Shell 绕过失败。

变更请求允许的长尾机制只有正式 `ShellArtifact`，并且必须同时满足：

1. Binder 已确认没有注册 Action 在语义上覆盖该目标；
2. 它不是为了隐藏参数、权限、前置条件、执行或验收失败；失败后的新 Artifact
   必须来自显式补证/Replan，并且是可说明的不同实施方案；
3. 脚本内容、绝对 cwd、run_as、最小环境、超时、预期变更和后置条件全部冻结；
4. 通过语法、AST、敏感信息、路径和破坏性目标策略校验；
5. 禁止命令替换、动态参数展开、嵌套解释器、后台执行和网络外传；
6. 内容进入计划哈希，接受精确的逐步审批；
7. Executor 使用固定 argv 和 `shell=False` 启动受控解释器；
8. Artifact 单次使用，超时或结果未知时不得自动重放。

`ShellArtifact` 是显式能力类型，不是 `step.command` 的兼容字段。若同类 Artifact 反复出现，应评估收敛为注册 Action，而不是把它固化成新的 Shell 模板旁路。

### 7.4 Executor

Executor 只执行已经审批且未漂移的冻结绑定。它不得：

- 自己选择替代命令或修复计划；
- 因退出码为 0 宣布目标成功；
- 对 `running`、`verifying`、超时或中断状态自动重放；
- 将 preview、dry-run 或未配置真实执行描述为已完成。

执行不确定时先检查当前环境，将结果交给 Verifier/Replanner 或人工决策。

## 8. 验证、失败与用户响应

- Checker 验证声明的后置条件；失败证据是 Verifier 的确定性下限，模型不能覆盖。
- Verifier 只根据整个用户目标所需的直接证据返回 `GoalOutcome`：`achieved`、`need_evidence`、`need_execution`、`need_replan`、`needs_user_decision` 或 `blocked`。
- 合同校验应检查“未解决项是否阻断目标判据”，不能因为存在任意 `uncertainties` 或 `missing_decisions` 就机械拒绝 `achieved`。
- Response 只整理终态事实，提升可读性；不得新增建议命令来假装补证，也不得把建议交给用户后声称流程完成。
- 只读清单优先由领域模型转换为自然语言或表格，突出平台、健康状态、运行角色、异常和证据来源，避免直接倾倒内部对象。
- 失败必须可见：说明阶段、根因、环境是否改变、已尝试恢复和下一步选项。
- 自动恢复尚有实质不同路径时走同一 Replan 循环；自动恢复耗尽或需要新授权时形成 `FailureRecord`，把人工加入循环。禁止异常直接结束且不给恢复入口。
- 执行后的确定性 Checker/后置条件失败必须先作为证据进入统一的执行后
  诊断与 Replan，不得立即转成人工 FailureRecord。超时、中断或环境是否改变
  无法确定时禁止自动重放，应直接暂停并进入人工决策。旧审批哈希不得用于
  重放失败实现；Replan 产生的新实现必须重新绑定并精确审批。
- `RecoveryOption` 只能表达用户级控制：继续处理、调整目标或范围、取消。不得把逐
  组件重启等 Planner 策略提升为失败类型或恢复动作。“继续处理”应把具体证据缺口、
  上一失败原因和已尝试路径传回同一 Planner/Discovery 循环，由原工作流决定具体
  策略；同一失败签名的继续路径没有进展后不得再次推荐。自动路径耗尽后只提供调整
  目标/范围或取消。
- Replan 应打印轮次、缺失事实、采用的补证边界以及结构化结果，但不得输出模型隐藏
  推理。no-progress 必须比较目标相关事实和刷新后的内容，不能只统计 Evidence key。

## 9. Prompt 的使用边界

Prompt 适合约束表达方式、请求模型输出结构化候选和提醒模型关注证据。以下约束必须由程序实现，不能只写在 Prompt 中：

- 状态迁移和当前活动目标；
- Plan/Failure 是否存在及其版本；
- Action、Probe、Checker 注册范围；
- Schema 和参数合法性；
- 权限、路径、风险、审批和重放策略；
- “目标已完成”的判据；
- 待决状态门与精确控制命令。

不得为某句用户话术在 Prompt 中加入正则式特判。新增提示规则前先判断它是否其实属于确定性合同或状态模型。

所有需要理解 Klonet 术语的模型阶段使用 `context.klonet_domain_context(role)` 的同一
份领域语义，并按 Intent、Planner、Binding、Discovery、Synthesis、Verifier、Response
职责裁剪。该上下文只定义词汇、角色和不变量，不是当前服务器证据；实例、路径、进程、
端口、解释器和健康状态仍只能来自 Discovery、`RuntimeInventory` 与冻结资源。领域提示
不能覆盖 Action 合同，Action 合同也不能反向承担自然语言理解职责。

## 10. 安全、文件与数据边界

- Mentor、Coding、Ops 和 Ops-Privilege 使用共享底层，但能力由 Profile 和工具注册边界隔离，不能各自复制框架。
- 所有聊天模型调用必须经过 `LLMClient → ProviderRouter` 唯一入口；Agent、Planner、Verifier、Response 和检索规划器不得自行读取供应商密钥、固定 base URL 或实现时间切换。Embedding/Rerank 的专用模型不混入聊天模型路由。
- 每个 `LLMClient` 必须默认具有有限单次请求超时且禁止 SDK 隐式重试；特定阶段只能显式收紧或按供应商最低需要放宽。一个 Ops-Privilege 工作流中的 Discovery、Synthesis、Planner、Binding、Verifier 和 Response 必须共享同一个 bounded 客户端。只有收到模型响应后的结构化合同错误才允许有限修复；连接失败或超时必须立即进入现有 fallback/FailureRecord，不能作为合同错误重复调用。
- 供应商限流属于统一传输策略。网关即使以 401 包装，只要结构化错误明确包含 rate-limit 语义，也应按限流处理：先轮换独立密钥，再执行次数和等待时间均有上限的显式退避。真正的认证失败只能逐密钥尝试一次；禁止无限循环或恢复 SDK 隐式重试。
- Coding 文件读写必须在 workspace 沙箱内；绝对路径必须解析并验证归属。
- 保留用户已有修改。遇到脏工作树时只改任务相关内容，不覆盖或清理不相关文件。
- 密码、token、私钥、cookie、Authorization 和 `.env` 正文不得进入 Prompt、计划、日志、记忆、命令参数或测试快照。
- 已审批 Action 的人工提权必须在现有 Executor/Direct Runner 边界内一次完成：先验证 sudo 凭据，随后所有实际命令强制使用 `sudo -n`。禁止让每条 Probe、前置检查或子命令分别弹出密码提示；一次认证失败必须立即形成结构化失败。
- 冻结到精确 PID/PGID 的组件动作只能检查该进程组。不得先扫描整机所有运行时再筛选目标，否则会扩大权限、证据和副作用边界，并可能因无关跨用户进程触发提权。
- 本机运行时 HTTP 检查（`localhost`、IPv4/IPv6 loopback）必须经过统一传输入口并强制直连，不能继承外部 HTTP 代理；远程 URL 保持默认代理策略。Discovery Probe、运行实例清单和执行后 Checker 不得各自实现不同的请求语义，证据必须注明实际传输方式。
- 运行态目录（如 `workspaces/`、`journals/`、`memory/`、trace 和缓存）不得被测试递归收集，也不得当成源码事实。
- 破坏性目标必须是字面、明确、已解析且有归属证据的资源；不得对根目录、HOME、workspace 根或未解析变量做递归操作。
- 不直接 push 主分支。安装依赖、联网、系统目录修改和外部状态变更遵守对应模式的审批边界。

## 11. 测试必须证明不变量

修复测试不得只匹配本次话术、目录、端口、计划 ID 或错误字符串。每个根因修复至少覆盖：

1. 原始失败场景；
2. 同类但不同输入的场景；
3. 相反方向的场景；
4. 既有功能不回退。

按变更层级增加测试：

- 路由：否定、纠正、继续旧目标、新目标、分类器错误和持久化状态冲突；
- 状态：合法迁移、非法迁移、重启恢复、旧记录不复活；
- Discovery：Probe 注册、去重、预算和无进展终止；
- Planner：语义完整性、互斥约束、不同实例/角色自然泛化；
- Binder：Action 优先、参数合同、无能力时的明确阻塞或正式 Artifact；
- Shell：允许的最小 Artifact、动态构造拒绝、敏感信息拒绝、未知执行不重放；
- Verification：目标级证据、无关不确定项、Checker 失败下限和相反结论；
- Response：不发明事实、不发明命令、结果可读且不改变状态。

优先使用 fake registry、临时存储和固定证据测试合同，不在测试中修改真实服务器。先运行最小相关测试，再运行相邻模块测试和完整套件；最后执行 diff 检查和 `git diff --check`。

提高循环上限、放宽校验、吞掉异常或更新快照让错误输出“通过”，都不算修复。

## 12. 代码与文档风格

- 命名直接表达领域含义；类和函数保持单一职责。
- 中文注释解释“为什么、边界和陷阱”，不逐行翻译代码。
- 优先复用现有 Registry、Contract、Store 和数据模型，不为了设计模式增加包装层。
- 结构化数据先于自由文本；自由文本只用于展示或模型语义候选。
- 异常应在有恢复语义的边界转换为明确状态；底层不得广泛吞异常。
- 新增字段必须定义所有权、持久化、迁移、失效和序列化行为。
- 设计文档应标注当前状态；被替代的文档应注明历史性质或删除，避免旧方案再次成为实现依据。
